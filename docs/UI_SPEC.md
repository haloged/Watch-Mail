# WearMail 圆形表盘 UI 规格说明

> 目标设备：466 × 466 px 圆形表盘，Wear OS 3.0+（API 30+）
> 本文档描述每个页面在圆形表盘上的**具体布局**、尺寸与交互，是 `ui/` 包实现的依据。

---

## 1. 坐标系与安全区

以屏幕左上角为原点，x 向右、y 向下：

| 项目 | 数值 | 说明 |
|------|------|------|
| 屏幕 | 466 × 466 px | 正方形像素阵列，物理显示为圆形 |
| 圆心 | (233, 233) | 内切圆（直径 466px）的圆心 |
| 物理圆半径 | 233 px | 超出该半径的像素被圆形遮罩裁掉（不可见） |
| **安全内容半径** | **210 px** | 核心内容必须落在此圆内 |
| 边缘缓冲区 | 23 px | 233 − 210，用于吸收字体渲染误差与抗锯齿 |
| 触控热区下限 | 48 × 48 px | 所有可点击目标 |
| 正文字号下限 | 14 px | 正文推荐 16–18px，标题 20–22px |

密度参考：该尺寸表盘通常 `density ≈ 2.0`，即 **1dp ≈ 2px**，屏幕约 233dp 见方。
代码中 `dp` 常量与本文档 `px` 数值的换算即按 density=2.0 给出。

## 2. 弦长表（列表项宽度的计算依据）

在高度 `y` 处，圆内可用水平宽度（弦长）为 `2·√(r² − (y−233)²)`。
**安全区半径 210px 是本项目的列表收窄依据**；最右列即该项需要留出的单侧水平内边距。

| y (px) | 距圆心 (px) | 安全区弦长 (r=210) | 物理圆弦长 (r=233) | 单侧内边距 |
|-------:|-----------:|------------------:|------------------:|----------:|
| 23 | 210 | 0.0 | 201.9 | 233.0 |
| 40 | 193 | 165.5 | 261.1 | 150.2 |
| 50 | 183 | 206.0 | 288.4 | 130.0 |
| 68 | 165 | 259.8 | 329.0 | 103.1 |
| 88 | 145 | 303.8 | 364.8 | 81.1 |
| 104 | 129 | 331.4 | 388.1 | 67.3 |
| 130 | 103 | 366.0 | 418.0 | 50.0 |
| 160 | 73 | 393.8 | 442.5 | 36.1 |
| 200 | 33 | 414.8 | 461.3 | 25.6 |
| **233** | 0 | **420.0** | 466.0 | 23.0 |
| 266 | 33 | 414.8 | 461.3 | 25.6 |
| 306 | 73 | 393.8 | 442.5 | 36.1 |
| 350 | 117 | 348.8 | 403.0 | 58.6 |
| 378 | 145 | 303.8 | 364.8 | 81.1 |
| 400 | 167 | 254.6 | 325.0 | 105.7 |
| 413 | 180 | 216.3 | 295.9 | 124.8 |
| 430 | 197 | 145.5 | 248.8 | 160.3 |
| 443 | 210 | 0.0 | 201.9 | 233.0 |

实现位置：`ui/kit/CircularMetrics.kt`（纯函数）+ `ui/kit/CircularSafeLazyColumn.kt`（滚动列表）。

**关键结论**：如果按物理圆（233px）铺满，在 y=23 处仍"看似"有 201.9px 宽度，
但内容会紧贴圆弧边缘、抗锯齿后文字被切；按安全半径 210px 计算虽然更窄，
却能保证任何字重、任何字号下都不被裁切。

## 3. 通用三段式分区

```
        ┌───────────────────────────┐   y = 0
        │  ① 顶部弧形区（状态栏）    │   时间（TimeText 弧线文字）、同步状态
        │      y ≈ 0 – 104 px       │
   ┌────┴───────────────────────────┴────┐
   │                                      │
   │        ② 中部圆形安全区               │   y ≈ 104 – 400 px
   │      半径 ≤ 210px 的内容区            │   主体：列表 / 表单 / 正文
   │                                      │
   └────┬───────────────────────────┬─────┘
        │    ③ 底部弧形区（操作）    │   y ≈ 400 – 466 px
        └───────────────────────────┘   主按钮、电量、操作栏
```

| 分区 | 收件箱实际占用 | 实现方式 |
|------|--------------|----------|
| ① 顶部弧形 | 0 – 168 px（0 – 84dp） | `TimeText` 弧形文字 + 账户筛选胶囊（48dp）；列表 `contentPadding.top = 84.dp` |
| ② 中部安全区 | 168 – 382 px（84 – 191dp） | **信息流主体**；每项宽度由 `CircularItem` 按弦长动态收窄 |
| ③ 底部弧形 | 382 – 466 px（191 – 233dp） | 紧凑主按钮「新建邮件」（48dp、内容宽度）+ 底边距 26dp；列表 `contentPadding.bottom = 84.dp` |

### 3.1 纵向预算（信息流空间为什么这么设计）

圆形表盘高度只有 233dp，顶部要给时间弧线与筛选器、底部要给主按钮，
**中间剩下的才是信息流**，所以顶部/底部的固定占比必须压到最小：

| 版本 | 顶部占用 | 底部占用 | 中间干净可视带 |
|------|--------:|--------:|--------------:|
| 早期版本 | 88dp | 136dp | `233−88−136 = 9dp`（不到一行邮件） |
| 上一轮（紧凑胶囊） | 84dp | 84dp | `233−84−84 = 65dp`（约 1.5 行，提升约 7 倍） |
| **当前（按钮减半）** | **56dp** | **54dp** | `233−56−54 = 123dp`（约 3 行，比上一轮再提升约 **89%**） |

腾出空间的三个关键改动：

1. **状态信息（电量 / 最近同步 / 设置入口）从固定底栏改为列表尾项**（`InboxScreen.StatusBar`）：
   信息不丢（滚到底即可看到），但不再固定占用 30–40dp。
2. **底部主按钮改为「内容宽度胶囊」并贴近底部**（底边距由 64dp 降到 22dp）：
   y=211dp 处可用弦长约 91dp，整行 52dp 大按钮放到这个高度会被圆弧切掉两端；
   迷你胶囊约 83dp 宽，可安全落到该位置并留约 4dp 余量。
3. **按钮减半（本轮）**：筛选胶囊与底部主按钮由 48dp 改为 **24dp 迷你件**
   （`MiniActionButton` / `MiniOptionButton`），顶部与底部两条带子合计由 168dp 降到 110dp。
   24dp 在本机密度（≈2.0）下正好是 **48px**，恰好等于需求要求的最小触控热区 ——
   这是「不能再小」的硬下限，不要继续压缩。

为什么不能用 `CompactButton` 加 `Modifier.height(24.dp)` 来实现减半：
它内部固定 48dp 高（`CompactButtonDefaults.Height`），从外部压高度只会**裁切内容**；
因此两个迷你件用 `clip + background + clickable` 自绘（见 §4.1）。

详情页同理：操作栏底边距由 54dp 降到 **42dp**（三个 48dp 图标按钮共 144dp，
y=191dp 处弦长约 148dp，是几何允许的下限附近），并把正文列表的底部内边距
由 66dp 提到 **96dp**，避免最后几行正文被固定操作栏盖住（原值小于操作栏占用高度，属于真实缺陷）。

`dp → px` 换算（density = 2.0）：56dp = 112px，54dp = 108px，42dp = 84px，24dp = **48px**，22dp = 44px，14sp ≈ 28px。

## 4. 通用组件规格

| 组件 | 规格 | 位置 |
|------|------|------|
| 状态栏时间 | Wear `TimeText`（弧形文字，系统 12/24 小时制） | 顶部弧线 |
| 电量 | `labelSmall`（≈12–14sp），形如 `82%` | 底部弧形，居中偏下 |
| 页面标题 | `titleMedium`（≈20sp） | 安全区顶部 |
| 列表主行（发件人） | `bodyMedium`（≈16sp），单行截断 | 列表项第一行 |
| 列表次行（主题） | `bodySmall`（≈14sp），单行截断 | 列表项第二行 |
| 时间戳 | `labelSmall`（≈12–14sp）**不小于 14sp** | 列表项右上 |
| 账户标识 | 9px 圆点（`AccountDot`）或 24dp 圆形首字母徽标 | 列表项左侧 |
| 未读标记 | 7px 主色圆点 + 主题加粗 | 列表项左侧 |
| 主按钮 | `PrimaryActionButton`，高度 ≥ 48dp | 底部弧形区 |
| 图标按钮 | `IconButton`（Wear 默认触控热区即满足 48dp） | 详情页底部操作栏 |

**触控热区**：Wear Material3 的 `Button`/`IconButton`/`Card` 默认带
`minimumInteractiveComponentSize`，但本项目额外用 `Modifier.heightIn(min = 48.dp)`
保证自绘行也满足 48dp 下限（`CircularMetrics.meetsTouchTarget` 有对应单元测试）。

### 4.1 按钮尺寸层级（重要，易踩坑）

Wear Material3 的 `Button` 容器高 **52dp 且占满整行**（`FilledButtonTokens.ContainerHeight`），
若把「选项 / 筛选项」也用它，圆形表盘上会立刻变成一摞巨型胶囊
（添加账户页曾出现 **14 条**整行大按钮，一屏放不下两个字段）。因此本项目规定：

| 用途 | 组件 | 尺寸 | 依据 |
|------|------|------|------|
| 页面**唯一主操作**（新建邮件 / 发送 / 保存账户 / 下一步 / 立即同步） | `PrimaryActionButton`（Wear `Button`） | 高 52dp、整行 | Wear 主操作规范 |
| **次要操作**（自动探测 / 验证连接 / 用手机扫码配置） | `SecondaryActionButton`（Wear `CompactButton`） | 高 48dp、**内容宽度** | 不与主操作抢视觉重心 |
| **单选组**（服务商预设 / 加密方式 / 同步频率 / 发件账户）、常用联系人 | `CompactOptionButton` + `CompactOptionGroup`（`FlowRow` 自适应换行） | 高 48dp、**内容宽度**、每行放得下几个就放几个 | 一组选项只占一个列表项 |
| **信息流页的固定操作条**（收件箱「新建邮件」）+ **筛选项** | `MiniActionButton` / `MiniOptionButton` | 高 **24dp**（= 52dp 按钮的一半）、内容宽度 | 圆屏纵向预算紧张，固定条每多 1dp，信息流就少 1dp |
| 对话框内选项 | Wear `Button` | 高 52dp、整行 | 模态场景整行更易点按 |

关键实现（`ui/kit/Components.kt`）：

- `CompactOptionButton`：选中态 = 主色填充 + ✓；未选中 = `surfaceContainerHigh` 填充。
  它继承 `CompactButton` 自带的 tap target padding，**触控热区仍 ≥ 48dp**（需求 1.2 不破）。
- `CompactOptionGroupOf(labels, selectedIndex, onSelect)`：把整组选项放进**同一个列表项**，
  用 `FlowRow` 换行 —— 这是消除「一列大按钮」的关键。
- 效果：添加账户页的「5 个服务商 + 3 种登录方式」由 8 条整行胶囊（约 416dp 高）
  变为 2 个换行选项组（约 250dp 高），纵向占用减少约 40%，且视觉上不再是整行巨条。
- **迷你件（本轮新增）**：`MiniActionButton` / `MiniOptionButton` 高度固定 **24dp**，
  用 `clip(CircleShape) + background + clickable` 自绘 —— 之所以不用 `CompactButton`，
  是因为它内部固定 48dp 高（`CompactButtonDefaults.Height`），外部压高度只会裁切内容。
  合规性：24dp × density 2.0 = **48px**，恰好满足「触控热区 ≥ 48×48px」，因此是下限。
  ⚠️ `MiniOptionButton` 的 `leading` / `trailing` 不会自动继承选中态颜色，
  调用方需按 `selected` 自行着色（见 `InboxScreen.FilterChip` 的未读数）。

### 4.2 覆盖层规范（背景不透明 + 拦截指针事件）

详情 / 撰写 / 添加账户是画在顶部分页**之上**的覆盖层（`OverlayRoute`），
它们与分页是同一个 `Box` 的兄弟节点。由此有两条硬性要求：

1. **根节点必须自己绘制不透明背景**。
   分页页面背后是 Activity 的黑色窗口，所以"不画背景"在分页上看不出问题；
   但覆盖层一旦透明，空白处就会直接透出下面的收件箱 ——
   这正是「添加账户页能看到上一页内容」的根因。
   实现：`CircularScreen` 根节点统一 `.background(MaterialTheme.colorScheme.background)`，
   且所有 `*Screen.kt` 都必须通过它布局（不允许自建透明根节点）。
2. **覆盖层必须拦截指针事件**。
   否则空白处的点击/滑动会穿透到分页，造成误切换页面或误开邮件。
   实现：`WearMailNav` 在**内容层之下、分页之上**加一层
   `fillMaxSize().background(...).pointerInput { 消费所有 PointerEvent }` 遮罩；
   因为它在内容层之下，不会干扰覆盖层自身的点击（命中测试优先取最上层节点）。

两条规则都有对应的静态检查（`tools/static_checks.py` 的「覆盖层不透明且拦截指针」），
可防止此类回归。

**振动反馈**（`ui/kit/Haptics.kt`）：

| 语义 | 模式 | 触发点 |
|------|------|--------|
| `tick()` | 单次 18ms | 点击邮件、切换筛选项、进入详情 |
| `longPress()` | 单次 40ms | 长按弹出操作菜单 |
| `success()` | 短-短（28/70/28ms） | 发送成功、同步完成 |
| `error()` | 长-更长（60/90/140ms） | 发送失败、认证失败、删除失败 |

### 5.2 添加账户（AddAccountScreen）

三步式表单（手表输入困难，尽量减少单页字段数）：

| 步骤 | 内容 | 控件 |
|------|------|------|
| 1/3 邮箱 | 邮箱地址、别名、密码/授权码、服务商预设 | `WearTextField`（Email 键盘 / Password 键盘）+ 预设按钮组 |
| 2/3 服务器 | IMAP 主机/端口/加密、SMTP 主机/端口/加密；「自动探测」 | `WearTextField`（Number 键盘）+ 加密方式按钮组 |
| 3/3 验证 | 「验证连接」「保存账户」；**手机扫码配置入口** | 按钮 + 二维码展示 |

扫码配对子界面：

```
   ┌──────────────────────────┐
   │   用手机扫码配置邮箱        │
   │   ┌──────────────────┐   │
   │   │   ▓▓▒▒▓▓ QR ▓▓▒▒ │   │  300×300px 二维码（居中，位于安全区内）
   │   └──────────────────┘   │
   │   http://192.168.1.7:8080 │  labelSmall，超长截断
   │   手机与手表需在同一 Wi-Fi  │  提示文案
   │   已保存 1 个账户           │  实时状态
   └──────────────────────────┘
```

- 二维码由 ZXing 生成（纠错级别 M，白底黑块），手机与手表同一 Wi-Fi 时扫码即打开填写页面；
- 离开页面 `DisposableEffect.onDispose` 立即关闭本地 HTTP 服务并释放端口；
- 未连接 Wi-Fi 时显示「未连接 Wi-Fi，无法扫码配对」，并引导手动填写。

OAuth2（Outlook）授权面板 —— 步骤 1 选中「OAuth2 令牌」时，**替换**「密码 / 授权码」输入框：

```
   ┌──────────────────────────┐
   │   Microsoft 账号授权        │  SectionHeader
   │  Outlook/Office 365 已停用  │  labelSmall（说明为什么不能用密码）
   │        密码登录，需授权      │
   │                          │
   │        ABCD-EFGH          │  titleLarge + letterSpacing 2sp（核心信息，一眼可读）
   │   在手机浏览器打开网址输入    │  labelSmall
   │   ┌──────────────┐        │
   │   │  ▓▓▒▒▓▓ QR   │        │  132dp 显示（按 300px 生成，纠错级别 M）
   │   └──────────────┘        │
   │  microsoft.com/devicelogin │  labelSmall，超长截断
   │  ◐ 等待授权…（剩余 300s）   │  转圈 + 进度文案
   │        [ 取消 ]            │  CompactButton（内容宽度）
   └──────────────────────────┘
```

- 未配置客户端 ID 时，同一位置显示注册指引文案（**不跳转设置页**：导航层不归本页管）；
- 已授权后显示「已授权（有效期至 HH:mm）」+「重新授权」按钮；
- 微软不支持在授权链接里预填短码（无 `verification_uri_complete`），
  因此二维码只承载授权网址，短码仍需在手机上手动输入；
- 面板**不接触任何令牌**：令牌只存在于 ViewModel 私有字段，界面只显示"是否已授权 + 有效期"。

| 列表 | 中部安全区 | `CircularSafeLazyColumn` + `itemsIndexed`，`key = mail.id` |
| 列表项 | 宽度按弦长收窄 | 第一行：账户色点 + 发件人 + 时间；第二行：主题（单行截断） |
| 未读 | 行内 | 主题 `FontWeight.Bold` + `UnreadDot()`；已读用 `onSurfaceVariant` |
| 错误条 | 列表首项 | `ErrorBanner`（点击重试），不弹 Toast（圆屏易被裁切） |
| 空态 | 中部 | 无账户 → 「去添加账户」；有账户无邮件 → 「下拉刷新」 |
| 底部 | 弧形区 | 电量百分比 + 最近同步相对时间；「新建邮件」主按钮 |

交互：
- **上下滑动**：滚动列表（表冠同样生效）；
- **下拉刷新**：基于 NestedScroll 的下拉手势，超过 48dp 阈值触发 `syncAll(MANUAL)`；
- **点击**：进入邮件详情；
- **长按**：弹出操作菜单（标记已读/未读、标星、删除），删除二次确认；
- **左滑 / 右滑**：切换顶层页面（见 §6）。

## 6. 手势与输入映射

| 输入 | 行为 | 实现 |
|------|------|------|
| 上下滑动 | 滚动当前列表 | `LazyColumn` |
| 下拉（列表已在顶部） | 刷新邮件 | `NestedScrollConnection`，阈值 48dp |
| 左滑（顶层页） | 收件箱 → **账户管理** | `HorizontalPager` +1 页 |
| 右滑（顶层页） | 收件箱 → **设置** | `HorizontalPager` −1 页 |
| 点击 | 进入详情 / 执行操作 | `Card(onClick)` |
| 长按 | 弹出操作菜单 | `Card(onLongClick)` → `AlertDialog` |
| 表冠旋转 | 滚动当前活动列表 | `MainActivity.onGenericMotionEvent` → `RotaryBus` → `LazyListState.scrollBy` |
| 系统右滑退出 | **已禁用** | `themes.xml` 中 `android:windowSwipeToDismiss=false` |

**手势冲突与取舍（重要）**：

1. 需求中的「左右滑动删除邮件」与顶层「左右滑动切换页面」在手势通道上直接冲突
   （两者都是水平拖动）。本项目选择：**水平滑动用于页面切换**（信息层级更高、
   误删代价更大），删除改为**长按菜单 + 二次确认**。这既满足"左右滑动切换页面"，
   又通过二次确认避免误删。
2. 系统级「右滑退出应用」被禁用，否则会与"右滑进入设置"抢同一个手势。
3. 顶部/底部弧形区域不放可滚动内容，避免手势与圆弧边缘误触。
4. 表冠事件由 Activity 统一接收后广播（`RotaryBus`），只交给"当前可见且无覆盖层"
   的页面，避免三个分页同时滚动。
